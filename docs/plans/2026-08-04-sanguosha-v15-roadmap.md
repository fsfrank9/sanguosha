## S 执行记录 (2026-08-05, 一批交付 S1+S2)

**范围**: 用户点单"一次性完成 S 阶段" → S1 (响应窗口打出流程) 与 S2
(声明菜单 16/16 + AI 全型启发) 同批交付。两者不可拆: S1 的"验假重开"
判例需要 S2 新增的「响应赌假」质疑面才能端到端复现 (否则 AI 对响应中
的声明恒不质疑), 拆开会留下非绿中间态。

### S1 响应窗口【打出流程】/【响应中的使用流程】

- **表驱动八窗口** (`guhuo.js GUHUO_RESPONSE_WINDOWS`): 闪应 杀/万箭/
  银月 (`shan-response`/`wanjian-response`/`yinyue-response`)、杀应决斗
  (`sha-duel-response`, 三属性分列)、杀应南蛮 (`aoe-sha-response`, 评审
  收口新增)、杀应借刀 (`jiedao-decision`, 评审收口放宽)、桃·酒应濒死
  (`dying-rescue`, 酒仅自救)、无懈应锦囊 (`wuxie-response`)。可声明牌名
  由引擎按窗口给出, UI 不自行推断。
- **声明期只定牌名**: 打出流程无"选择目标时"步骤、无"取消不合法的
  目标" (官方 `card__hero__neutral.md:336` 逐字), 目标由窗口自身确定;
  质疑链、亮出、缠怨与使用流程复用同一实现。
- **验假 = 窗口原样重开**: "视为你没有决定如何进行响应" — 原
  pendingChoice 对象回槽, 该窗口的 pauseState 未被触碰; 本回合限次已
  消耗, 重开窗内不能再蛊惑 (缘起表述"可再蛊惑"按 G4 更正)。
- **验真/无质疑 = 注入回原流程**: `pauseState.guhuoResponse` 携实体牌
  + 声明牌名, 由 `consumeResponse` / `consumeWuxie` / 濒死救援三个出口
  取用 (一次性消费, 未消费则退回手牌兜底)。实体牌面即最终牌面 → 银月
  枪等"回合外黑牌"时机照常按实体牌面派发。
- **开窗门槛放宽**: 于吉可背面朝上打出任意手牌 → 手上没有所需牌型也
  必须开窗 (此前"无闪不开窗/无懈不开窗"把蛊惑的响应面直接锁死)。六处
  gate 统一走 `guhuoResponsePossible` 谓词 (声明入口本身亦复用同一谓词),
  仅玩家席。
- **限次修正 (R1 遗留缺陷)**: "每名角色的回合内限一次"是按回合刷新的
  全场额度 (`rule__principle.md:58` 判例: 于吉在贾诩的回合内发动蛊惑)。
  原 `resetActorTurnState` 只复位回合主 → 响应面接入后额度会永久卡死;
  改由 `phases.resetGuhuoTurnLimit` 在每个回合开始清全场。
- **拦截口**: `resolvePendingChoice` / `resolveResponseChoice` 双
  dispatcher 在 `decision.guhuo` 时前置拦截 (声明是"如何响应"的另一条
  分支, 不是该 kind 的一个决策值); 校验失败窗口原样留槽, 零副作用。
- **UI**: `guhuoResponsePanel` 与所在响应窗口**并列**显示 (选牌名 +
  盖置手牌 + 确认门禁)。刻意不进 `PENDING_MODAL_DISPATCH` — hand-confirm
  快捷键留给主窗口的"打出真牌", 蛊惑走面板内自己的确认按钮。

### S2 声明菜单 16/16 + AI 全型启发

- **菜单补齐 11→16** (`mode-panels.js GUHUO_UI_TYPES`): 拆/顺/火攻 转
